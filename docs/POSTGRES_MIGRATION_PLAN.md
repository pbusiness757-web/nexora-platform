# PostgreSQL Migration Plan

## Current State

| Item | Value |
|---|---|
| `schema.prisma` provider | `postgresql` ✓ |
| `migration_lock.toml` provider | `sqlite` ⚠️ |
| Migration files (3) | Written in SQLite syntax |
| Database on VPS | PostgreSQL (initialised via `prisma db push`) |
| Migration history in DB | None — `db push` bypasses the `_prisma_migrations` table |

### Root cause

The project was developed with SQLite, then the schema was switched to PostgreSQL
(`provider = "postgresql"`) without regenerating migrations. The three existing
`.sql` files use SQLite-specific syntax:

- `PRAGMA defer_foreign_keys=ON` — SQLite only
- `PRAGMA foreign_keys=OFF` — SQLite only
- `DATETIME` column type — SQLite only (PostgreSQL uses `TIMESTAMP`)
- `TEXT NOT NULL PRIMARY KEY` — works in both but not idiomatic PostgreSQL

`migration_lock.toml` still records `provider = "sqlite"`, so
`prisma migrate deploy` will refuse to run and will throw:

```
Error: P3005 The database schema is not empty. Read more about how to baseline
your database: https://pris.ly/d/migrate-baseline
```

The VPS database is **live and healthy** because `prisma db push` was used
to create the schema directly, bypassing the migration engine entirely.

## Risks

| Risk | Severity | Notes |
|---|---|---|
| Running `prisma migrate deploy` now | 🔴 CRITICAL | Will fail or conflict with existing schema |
| Running `prisma migrate reset` | 🔴 CRITICAL | **Destroys all production data** — never run |
| Running `prisma migrate dev` on VPS | 🔴 CRITICAL | Development command, drops/recreates schema |
| Leaving `migration_lock.toml` as sqlite | 🟡 Medium | Blocks future `migrate deploy` usage |
| Future schema changes via `db push` | 🟡 Medium | Silent diffs; no rollback history |

## Safest Migration Strategy (Baseline Approach)

Prisma's official solution for this situation is **baselining**:
mark the current database state as the known baseline so the migration engine
can take over future changes without touching existing data.

### Step-by-step (do this once, in order)

**Step 1 — Backup the database (on VPS)**
```bash
pg_dump -U nexora nexora > /backups/nexora-before-baseline-$(date +%F).sql
```
Verify the backup is readable before continuing:
```bash
wc -l /backups/nexora-before-baseline-*.sql
```

**Step 2 — Replace the three SQLite migration files with one PostgreSQL baseline**

On your local machine, delete the old migrations and create a single baseline:

```bash
cd C:\CryptoPayout\nexora-platform\server

# Remove SQLite migration files (NOT the lock file yet)
rm -rf prisma/migrations/20260612135123_init
rm -rf prisma/migrations/20260614110839_add_rate_snapshot
rm -rf prisma/migrations/20260614111854_add_finance_fields

# Create the new baseline migration directory
mkdir -p prisma/migrations/0_baseline
```

Then generate a PostgreSQL-compatible SQL snapshot of the current schema:
```bash
npx prisma migrate diff \
  --from-empty \
  --to-schema-datamodel prisma/schema.prisma \
  --script > prisma/migrations/0_baseline/migration.sql
```

Review the generated file — it should contain PostgreSQL syntax only
(`TIMESTAMP`, no `PRAGMA`, proper `DECIMAL(18,2)` types).

**Step 3 — Fix `migration_lock.toml`**

Replace the file content:
```toml
# Please do not edit this file manually
# It should be added in your version-control system (e.g., Git)
provider = "postgresql"
```

**Step 4 — Mark the baseline as applied on VPS (does NOT run any SQL)**

```bash
ssh root@72.56.123.4
cd /var/www/nexora-platform/server
npx prisma migrate resolve --applied 0_baseline
```

This tells Prisma "this migration is already applied" without executing it,
because the database already has this schema via `db push`.

**Step 5 — Verify**

```bash
npx prisma migrate status
```

Expected output:
```
✔ Database schema is up to date!
```

**Step 6 — Commit and push**

```bash
git add server/prisma/migrations server/prisma/migration_lock.toml
git commit -m "chore: baseline postgres migrations"
git push origin master
```

## Future Schema Changes (after baseline)

All future changes must go through the migration flow, never `db push`:

```bash
# 1. Edit schema.prisma locally
# 2. Generate migration
npx prisma migrate dev --name describe_your_change
# 3. Review generated SQL
# 4. Deploy to VPS
npx prisma migrate deploy
```

---

## Rollback Plan

If anything goes wrong during baselining:

1. The baseline step (`migrate resolve`) writes only to the `_prisma_migrations`
   table — it does NOT alter application data. It is safe to undo:
   ```sql
   DELETE FROM _prisma_migrations WHERE migration_name = '0_baseline';
   ```
2. Restore from backup:
   ```bash
   psql -U nexora nexora < /backups/nexora-before-baseline-YYYY-MM-DD.sql
   ```
3. The application continues to work even without a baseline — `db push`
   remains available as a fallback.

---

## What NOT to Run

```bash
# ❌ NEVER on production
prisma migrate reset       # drops the entire database
prisma migrate dev         # development only, may drop schema
prisma db push --force-reset  # destroys all data
```
